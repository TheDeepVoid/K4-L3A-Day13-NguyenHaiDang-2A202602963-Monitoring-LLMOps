# CP3 - PREVENTIVE MEASURE: queueing was invisible to every signal
#
# Found during the investigation: the /chat handler is async, but it called
# the blocking LabAgent.run directly, which pins the event loop. Under
# concurrency every request queued behind the others, so the latency logged,
# put on the dashboard and judged by the SLO excluded the wait users actually
# went through.
#
# Workload is identical in both halves: python scripts/inject_incident.py
# --scenario rag_slow, then scripts/load_test.py --concurrency 5 (10 requests).
# Client numbers come from the load generator; server numbers from the log.

    min=5309  median=13266  max=14172  n=10

    min=2651  median=2651  max=3503  n=10
  gap between what the user felt and what the SLO measured:

Conclusion: on this workload the client-observed median fell from 13266 ms to
2655 ms and the maximum from 14172 ms to 3494 ms. More important than the
speed-up is the ratio: before the change the server-side number understated what
users waited for by 4.0x (3503 ms logged vs 14172 ms felt); after the change the
two agree to within 1% (3449 ms vs 3494 ms). The 2.65 s that remains in every
trace is the injected retrieval delay; the residual ~0.8 s is real contention
for the threadpool, and it is now written to the log and judged by the SLO
instead of being invisible in a queue.
