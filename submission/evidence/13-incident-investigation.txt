==========================================================================
ROOT CAUSE, FIX AND PREVENTION
==========================================================================
  Root cause : app/mock_rag.py::retrieve() holds the request for 2.5 s while the
               incident switch is on, and that entire wait sits inside the
               `retrieve-context` span. The model call is unchanged
               (generate-response stays at ~0.15 s, ttft 0.05 s) and the prompt
               version in the trace is the same as the baseline, which rules
               out both "the model got slower" and "someone changed the prompt".

  Fix action : stop the incident and serve the degraded path:
                 python scripts/inject_incident.py --scenario rag_slow --disable
               The permanent fix is a deadline on retrieval plus a cached
               fallback, so a slow index degrades quality instead of latency.

  Prevention : (1) the `slow_answers` alert on p95 > 3000 ms, and
               (2) the `retrieval_quality_drop` alert, both demonstrated firing
               in evidence/12-alert-evaluation.txt;
               (3) the `retrieve-context` observation itself - before CP2 the
               trace had a single node and this step was not localisable;
               (4) the queueing fix, because a retrieval that blocks the event
               loop would have hidden the 2.5 s behind a much larger number
               (evidence/14-queueing-before-after.txt).
